## How to reproduce a row

1. **Code.** Use the branch `caojx/qwen38-flash-1124` at the commit named in the row or any later commit (forms are frozen, so a later commit runs the same package). Map its `vllm-torchtpu` tree into every leg with `--map-dir <tree>:prefill:/root/cloud-devkit/vllm-torchtpu`, and the same for `decode` and `proxy`, as the q38 cars do.

2. **Recipe.** Use the bundle in `q38_bands/recipe_root/`. It is the q38 team's recipe root, reduced to what these 25 points import:
   - `recipes/inferencex/qwen-3.8/infx-qwen38-flash-agentx-disagg.jsonnet`: the standard recipe, md5 001d9623. The default is `Q38_STD=q38-1124`, and `Q38_STD=legacy` renders exactly as the recipe the posted jobs ran.
   - `recipes/lib/` (8 files). These are the q38 lib, which differs from cloud-devkit-recipes master in `cdk.agentx` and `cdk.common`.
   - `recipes/inferencex/qwen-3.8/infx-qwen38-flash-agentx-disagg.exos17.jsonnet` (md5 10e9d215) and `recipes/lib_exos_q38/` (4 files), for the Exos rows.
   - To use it with cdk, copy the bundle over a **dedicated** cloud-devkit-recipes checkout at the same paths. Do not use your main checkout, because the q38 lib replaces two lib files other recipes use. Then set `CDK_ROOT_DIR=<that checkout>`.
   - Master's recipes.yml already registers `infx-qwen38-flash-agentx-disagg` at that path. The Exos sibling needs a registration entry, which our root has at recipes.yml line 2080: `name: exos-infx-qwen38-flash-agentx-disagg`, `k8s_file: recipes/inferencex/qwen-3.8/infx-qwen38-flash-agentx-disagg.exos17.jsonnet`. Exos jobs run with `--cluster cdk-tpu-exos`.

3. **Params.** Pass the row's params file of record (`q38_bands/params/<file>.params`, one `KEY=VALUE` per line). Then apply the row's Add / Remove column:
   - **Add** the form keys, plus `Q38_STD=legacy` on the 3 header-sticky rows (B3 c200spk, B4 c192 T54f, HIX P1). On the Exos oxpd rows the Add column includes `Q38_OXPD_FORM=1`, which their params of record do not carry: on their own tree (w3 `2bc75911f5`) that package was the main package, and on this branch it is `_forms/oxpd`, which only `Q38_OXPD_FORM=1` selects.
   - **Remove** `Q38_OXPD_FORM`. In the HIX params it sits inside `PREFILL_EXTRA_SERVER_ENV` / `DECODE_EXTRA_SERVER_ENV`.
   - **Exos rows: not yet reproducible from this branch.** The Exos recipe's start-up bootstrap patches only the main package, not `_forms/<form>`; the posted Exos points ran plain trees, so their package was patched, but here the selected form would run unpatched. A recipe fix that also patches the selected form is in progress; until it is installed, do not run Exos rows from this branch (README "Notes").
   - **Exos rows:** replace `Q38X_EXPECT_SRC_HASH` with the SRC of the mapped head: `cd <tree> && find src -type f -name '*.py' -print0 | LC_ALL=C sort -z | xargs -0 sha1sum | sha1sum | cut -c1-10` (67279495a2 at d10495d454, 4633debdbc at 30f302533c). The params of record carry the old tree's value (f696bcf585). The 7 tune-oxpd rows also carry `Q38X_EXPECT_POST_HASH=031145cfb0`; whether the tree guard needs that changed too is U.
   - Example (B1 SB1-1): `cdk job create infx-qwen38-flash-agentx-disagg $(grep -v '^#' q38_bands/params/b1_sb11_c212.params) Q38_FORM=k_sb11 Q38_PROXY_FORM=k --map-dir ...`. The q38 launchers pass each params line as one argv element, so values with spaces stay whole. Do the same: do not word-split the file.
   - 9 files pass `DECODE_QWEN4_EXP_PD_STAGING_BYTES` twice: the 7 B1 / B3 / B4 standard files and the 1P1D r09i2 / r07 files, with 17179869184 first and 8589934592 later. The later value is the one the job rendered, so keep the files as they are.

4. **Env deltas** (`q38_bands/params/ENV_DELTAS.md`, one block per row):
   - **Standard-recipe rows:** every `<role>.env.*` key in the job's stored render that is absent from, or differs from, the standard served-shape render. These are the point's lever flags.
   - **Exos rows:** the lever-family exports of the stored render.
   - The deltas are informational. Passing the params file reproduces them; you do not set them by hand.
   - **No-op keys:** `USE_BATCHED_RPA_LONGCTX, TPU_RPA_DECODE_BATCHED, TPU_KV_BYTES_EXPLICIT, TPU_ATTN_MOE_OVERLAP, TPU_TP_HIERARCHICAL_ALL_REDUCE_MIN_TOKENS, DP_SCHED_BATCH_PREFILL, TPU_MOE_FUSED_EP_ASYNC_ROW_GATHER, TPU_MOE_FUSED_EP_STEP_MIN_TOKENS, TPU_TOKEN_BUCKET_LINEAR_INTERVAL, TPU_TOKEN_BUCKET_LINEAR_UNTIL` are set in the renders but read by no code in this tree (PSTEP-QSAX). They are marked "no-op in this tree (read by no code)" and kept for byte-exactness. On the standard-recipe rows they come from the recipe's own defaults, not from the point, so they are not deltas there.

5. **What has been proven (M):**
